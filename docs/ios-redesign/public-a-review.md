# 独立评审、修复与复审（公开整理）

本文整理针对本改版的独立只读源码评审（Codex）结论、作者的修复，以及针对修复的独立复审。评审是源码层面的，不等于编译、模拟器、真机或服务端鉴权验收。

## 1. 首轮独立评审

范围：改版功能代码（含当时尚在开发的语音分支），相对基线 `93729ff`。

结论：**0 项 P0、1 项 P1、若干 P2。** 本机/云端隔离、无伪造本机 AI 回复、通常情况下的写失败回滚基本符合设计；读取失败的分类存在可能覆盖旧数据的漏洞，应先修复。

### P1-01：读失败被当作「首次使用」，恢复访问后可能覆盖旧库

- **问题**：`Data(contentsOf:)` 的任何错误都进入同一个 catch，随后只用 `FileManager.fileExists(atPath:)` 的布尔值分类。该查询无法区分「文件确实不存在」与「因父目录访问权限等原因无法确定是否存在」。已有数据文件的父目录暂时不可遍历时，读取失败且存在性查询返回 false，代码把它当成首次使用：空文档、可写。
- **后果**：访问恢复后，无需重启或重读，下一次发送、新建或草稿防抖保存就可能把空库衍生的新文档原子替换到原路径，丢失旧的对话、任务和记忆；界面也不会提示只读。原子写不能防止写入错误的空库。
- **评审建议**：只有明确确认文件不存在的错误才能初始化空库；权限、保护、其他 I/O 错误一律只读，恢复后须显式重读旧文档再允许提交；不要用第二次布尔存在性查询代替错误分类。
- **证据边界**：由源码分支与文件查询语义推出的条件性数据丢失路径，当时尚未在 iOS 上复现；不声称普通锁屏必然触发。

### P2

- **P2-01**：顶部边界卡和只读恢复卡是滚动区第一项，长对话时可能滚出视口。底部仍有本机/只读提示，不判为伪造 AI 或假同步。
- **P2-02**：任务完成按钮最小 32×32；消息行使用小号控件，更多菜单高 32，未达到 44pt 点击区。
- **P2-03**：评审收到的源码包不含 `scripts/check-invariants.py`，无法复核该检查；不据此认定完整仓库缺失（完整仓库中存在该脚本）。
- **沿用 P2**：云端 token 仍在 UserDefaults，属于已披露、本次未变更的凭证保护欠账。

### 评审确认的非问题（客户端静态范围）

- 本机/云端隔离成立，未发现登录时迁移、上传或合并本机内容的路径。
- 未发现硬编码账户数据或凭证。
- 无伪造本机 AI 回复、假理解、假同步；记忆查找确为字符串包含匹配。
- 云端问答是既有能力，示例数据只在 DEBUG 中。
- 写失败不会显示假成功；损坏和未来版本文件进入只读，不删除原文件（P1-01 为例外）。
- 工程成员、唯一入口完整，未放宽 ATS。

## 2. 修复（本发布包含）

- `LocalStore.reload()`：删除 `fileExists` 二次查询。只有读取错误本身是 `CocoaError.fileReadNoSuchFile`（底层 ENOENT）时才初始化空的可写库；权限不足（父目录不可遍历时为 EACCES）、文件保护、读到目录及其他 I/O 错误一律 `.unreadable` 只读。若平台把「不存在」报成其他错误，结果是保守只读（可通过重新读取恢复），不会丢数据。
- 只读状态下 `commit` 在编码、建目录、写盘之前直接抛错；权限恢复不会自动解除只读，只有显式 `reload()` 成功才解除。
- `LocalModel.reload()`：重读成功后，若磁盘旧草稿与只读期间的新输入不同且不是前缀关系，合并为「旧草稿 + 换行 + 新输入」，避免静默覆盖。
- 回归自测（`ios/Tests/LocalStoreSelfTest/main.swift` 第 10 节）：写入旧记忆和旧草稿并记录原始字节 → 父目录权限置 0 → 新建 store 必须为 `.unreadable` 且不暴露数据 → 恢复权限但不重读 → 写草稿必须抛 `.unreadable` 且文件字节完全不变 → 显式重读找回旧条目和旧草稿、可写 → 重新打开仍保留旧条目。权限恢复放在 `defer` 中；如果环境无法制造权限拒绝（root/ACL），测试打印 `UNSUPPORTED` 并计为失败，不会静默通过。

P2-01、P2-02 与 token 存储**未在本发布中修改**，仍为延后项。

## 3. 针对修复的独立复审

结论：**P1-01 可清零（源码复审层面）；Mac 运行验收需另行补证。**

复审要点：

- 首次使用只接受读取异常自身的 `fileReadNoSuchFile` 分类，已删除布尔存在性判断；其他读取错误进入只读，不再把「不确定是否存在」转换成可写空库。
- 只读时 `problem` 保留，`commit` 在任何磁盘操作之前抛错；权限恢复不会自动清除，只有可接受的 `reload` 结果能解除，且先完整解码旧文档再清除问题。
- 草稿定时保存、离开前台保存都经 `saveDraftNow`，会检查只读；发送、新建、编辑、完成、删除、转存都经 `apply` → `commit`。没有发现另一个直接写本机 JSON 或删除旧文件的生产路径；无法定位默认目录时为 `.unavailable`，也没有可写的替代库。
- 显式重读成功后，后续写入基于恢复后的磁盘文档构造，旧条目不会因此前空的界面文档而被替换。
- 新回归覆盖原 P1 的关键顺序，旧实现下应失败；无法制造权限拒绝时明确失败。

复审列出的残留风险与边界：

1. 新自测只编译 `LocalStore`，不覆盖 `LocalModel` 的 600ms 防抖、后台立即保存和重读后草稿合并；这些只经静态核对。
2. 「文件不存在」判断与后续原子替换之间没有排他创建或磁盘版本检查：若有另一个写入者在首次提交前创建文件，或加载后外部替换文件，后续提交可能覆盖更新的内容。正常单一 `LocalModel` 使用中未发现这样的第二写入者。
3. 「原字节不变」的保证针对被拒绝的写入和重读阶段；重读后用户正常保存会改写文件，此时应核对旧数据语义保留，而不是字节恒等。
4. iOS 文件保护（首次解锁前）的实际读取错误须在测试设备上验证，macOS 上的 chmod 回归不能替代。
